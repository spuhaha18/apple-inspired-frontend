# Apple-inspired Frontend v2 — 실행형 웹 스킬 설계

## 상태와 승인 경계
- 사용자 승인: 웹 프론트엔드 우선, 네이티브는 참고 범위. 공통 실행 절차·패턴·프로젝트 분기·실제 평가 방향.
- 본 문서: 상세 설계 검토안. 구현 착수 전 사용자 검토를 받는다.
- 원격 기준: spuhaha18/apple-inspired-frontend main 54450791f9184e6f2378c9097d5e975505f72c0e.
- GitHub push/PR/merge, 설치 스킬 교체, 타 프로필 변경은 이번 설계 작업에 포함하지 않는다.

## 목표
Claude Code와 Codex를 우선 실구동 검증 대상으로 삼고 다른 에이전트도 읽을 수 있는 도구 중립적 실행 스킬을 만든다. 같은 화면을 반복 생성하는 것이 아니라 조사→판단→구현→검증 과정의 일관성을 높인다. 기존 브랜드·사용자 요구·프로젝트 디자인 시스템을 우선하며 Apple HIG는 설계 근거로 사용한다.

## 비목표
React 전용 컴포넌트 라이브러리, 네이티브 구현, Apple 문서/디자인 자산 재배포, 모든 에이전트 자동 인식 보장, WCAG/GxP 인증, 사용자의 요구를 넘어선 제품 기획은 제공하지 않는다.

## 작업 모드
1. 신규 설계: 진단→명세→방향 승인→대표 화면→검증/수정→확장.
2. 기존 개선: 현재 화면·코드 진단→문제 근거→변경 명세→필요한 방향 승인→구현/검증.
3. 작은 변경: 기존 명세 읽기→영향 범위만 기록→구현/회귀 검증. 전체 명세 재작성과 무관한 리팩터링 금지.
4. 리뷰: 조사→실제 근거 수집→심각도·권고·미검증 보고. 요청 없는 코드 변경 금지.
기존 승인 명세 안의 실행은 반복 승인을 요구하지 않는다. 브랜드/탐색/핵심 동작 변경이나 범위 확장은 합의한다.

## 공통 행동 계약
### 진단
프로젝트 지침, 의존성, 라우팅, 전역 스타일, 토큰, 공통 컴포넌트, 관련 테스트를 읽는다. 기존 앱을 실행할 수 있으면 대표 화면을 확인한다. 핵심 작업, 환경, 재사용 자산, 변경 범위, 미확인 사항을 기록한다. 코드에서 찾을 수 있는 정보는 사용자에게 되묻지 않는다. 실행 불가 이유는 명시한다.
### 판단
모드와 프로젝트 유형을 선택하고 관련 패턴만 읽는다. 기존 브랜드와 정보 밀도를 유지할 부분과 변경할 부분을 구분한다. 확정되지 않은 고위험 선택만 질문한다. 독자적인 권장값을 Apple 공식 수치로 표현하지 않는다.
### 명세
주 행동, 정보 위계, 화면 구조, 토큰, 정상/로딩/빈 결과/오류/성공/권한 제한, 반응형, 키보드, 오류 복구를 정의한다. 해당 없는 상태는 이유를 기록한다. 새 방향은 구현 전에 합의한다.
### 구현
기존 스택·컴포넌트·토큰을 재사용한다. 큰 작업은 대표 화면을 구현하고 실제 검토 후 확장한다. 상태별 동작을 함께 구현하며 예시 데이터는 실제 업무 데이터로 오인되지 않도록 표시한다.
### 검증 및 수정
기존 테스트, 관련 상호작용, 접근성, 실제 화면을 검증한다. 문제를 수정한 후 영향 항목을 재검증한다. 환경/권한이 막히거나 제품 의사결정이 필요하면 구체적인 차단 원인과 최소 다음 조치를 보고한다. 미실행 테스트를 PASS로 표시하지 않는다.
### 인계
변경 파일, 승인된 결정, 실제 명령과 결과, 화면 증거, 남은 문제를 기록한다. 다른 에이전트가 대화 이력 없이 명세와 검증 기록을 읽고 이어받을 수 있어야 한다.

## 패턴 작성 규격
각 패턴은 사용 조건, 선택 규칙, 예외, 구성 요소, 상태, 작은 화면, 키보드/접근성, 좋은/나쁜 예, 검증 방법을 포함한다. 출처는 Apple 원칙/웹 기준/스킬 자체 제안으로 구분한다.
예: 행 간 비교가 핵심이면 표를 우선 검토하고 개별 시각 탐색이 핵심이면 카드를 검토한다. 모바일에서 숨긴 필드의 접근 경로를 정의한다. 입력 저장 실패 시 값을 유지하고 필드 오류와 서버 오류를 구분한다. 저장 응답 전 성공 표시를 하지 않는다.

## 에이전트 호환성과 제한
공통 본문은 Markdown, 상대 경로, 표준적인 이름/설명 메타데이터를 중심으로 구성한다. 특정 MCP/브라우저/패키지 설치를 필수 전제로 삼지 않는다. 설치 위치와 호출법은 각 제품 공식 문서로 재확인한다.
- 파일 접근만 가능: 분석·명세·리뷰는 가능. 실행/시각 검증 불가를 기록한다.
- 셸 가능: 프로젝트에 이미 있는 테스트를 실행한다. 의존성 추가는 범위와 승인을 확인한다.
- 브라우저 가능: 실제 상태·키보드·반응형을 확인한다.
- 스크린샷을 볼 수 없음: 캡처 생성과 시각 평가를 구분한다. 사용자 검토 또는 이미지 열람 가능한 검증자가 필요하다.
문서상 지원, 구조 확인, 실구동 확인을 별도로 표시한다. Claude Code/Codex 외의 제품을 테스트 없이 검증 완료라고 쓰지 않는다.

## 평가 설계
고정된 동일 입력과 초기 코드로 스킬 없음/현행판/v2를 비교한다. 각 실행은 깨끗한 작업 디렉터리에서 수행한다. 모델 ID·에이전트 버전·설정·도구·시점·사용 토큰/시간(확보 가능한 경우)을 기록한다. 비밀정보와 사내 자료는 테스트 입력에서 제외한다.
과제: 업무 표+검색/필터, 모바일 폼+오류 복구, 브랜드 랜딩페이지, 기존 화면의 작은 수정.
평가: 요구 충족, 기존 시스템 재사용, 시각 위계/일관성, 상태/복구, 접근성/반응형, 변경 범위 준수, 검증 정직성.
각 축 0=누락/실패, 1=부분 충족, 2=근거 있는 충족으로 기록한다. 접근성 적합성 자체는 점수만으로 선언하지 않는다. 결과물과 테스트 기록을 근거로 평가하고 평가자가 사용 변형을 모르게 할 수 있으면 블라인드 검토한다.
스킬 효과와 모델 차이를 혼동하지 않도록 동일 에이전트/모델 안에서 우선 비교한다. Claude Code와 Codex 각각 반복 실행 후 실패 유형과 결과 편차를 보고한다. 실행 예산/접근 권한이 부족하면 제한된 파일럿으로 명시하고 범용성 입증으로 확대하지 않는다.

## 수용 기준
- 네 모드의 시작 조건·행동·산출물·완료 조건이 모두 명시된다.
- 모든 로컬 상대 링크와 템플릿 경로가 유효하다.
- 핵심 판단과 패턴은 인터넷 조회 없이도 사용할 수 있다. 최신 Apple 정책/자산 권한이 필요한 경우 공식 출처 확인을 요구한다.
- 명세 예시에는 완성된 결정과 이유가 있으며 템플릿 빈칸을 예시로 제출하지 않는다.
- 제품별 경로·호출법은 확인 수준과 함께 기록한다.
- Claude Code와 Codex의 실제 실행 결과가 없으면 실구동 검증 완료를 선언하지 않는다.
- 코드/DOM 테스트와 시각 검증을 구분한다.
- Apple 자산·내부 수집본·개인 경로·비밀정보를 배포물에 넣지 않는다.

## 단계별 전달
1. 본 상세 설계 검토 및 승인.
2. 파일별 구현·테스트 계획 작성.
3. 공통 실행 본문, 패턴, 템플릿, 예시 구현 및 구조 검사.
4. Claude Code/Codex 파일럿과 결과에 따른 수정; 후속 비교 평가의 비용/범위 확정.
5. 검토 결과 보고. 원격 반영과 설치 교체는 별도 승인 범위로 처리.
