# 프로젝트 진단에서 인계까지

## 1. 읽을 범위를 정한다
프로젝트 지침 → 관련 패키지의 실행 스크립트/의존성 → 승인 명세 → 대상 경로/라우트 → 전역 토큰 → 재사용 컴포넌트 → 관련 테스트 순으로 읽는다. 저장소 전체와 원격 문서를 무차별로 읽지 않는다. 실행 명령은 프로젝트 문서/스크립트에서 확인한다. 기존 수정사항은 보존하고 사용자 변경과 내 변경을 구분한다.

진단 메모는 `핵심 사용자 작업 / 프로젝트 유형 / 모드 / 영향 파일 / 재사용 근거 / 사용 가능한 도구 / 미확인` 순서로 쓴다. 앱 실행이 가능하면 대표 화면을 확인한다. 실행할 수 없으면 실패한 명령과 원인 또는 도구 부재를 적는다. 코드에서 확인 가능한 스택/색상/라우트는 사용자에게 다시 묻지 않는다.

## 2. 문서 범위를 정한다
- 신규 설계: DESIGN에 주 행동과 구조를 먼저 작성한다. 사용자가 방향을 승인하면 대표 화면을 만든다. 승인 요청에는 미정 선택과 영향만 담는다.
- 기존 개선: 재현 가능한 문제, 유지할 부분, 수정할 부분을 분리한다. DESIGN은 영향 절만 갱신한다. 기존 명세가 없고 여러 흐름이 바뀌면 해당 흐름의 DESIGN을 작성한다.
- 작은 변경: CHANGE에 승인 근거·범위·재사용·상태·검증을 기록한다. 전체 DESIGN 생성은 이 모드의 작업이 아니다. `docs/changes/` 등 프로젝트 관례를 우선하고 없으면 `CHANGE.md`를 사용한다. 기존 기록은 덮지 말고 항목을 추가한다.
- 리뷰: REVIEW를 작성하고 구현 파일은 그대로 둔다. 코드가 아니라 원인이 불명확한 외관만 보이면 그 사실을 증거 수준으로 표시한다.

## 3. 결정과 승인 경계
사용자가 이미 승인한 명세/국소 요구가 있으면 그 범위에서 바로 실행한다. 색상 체계 교체, 탐색 구조 이동, 제출/삭제 의미 변경, 의존성 추가, 화면 확장이 필요하면 선택지·이유·영향을 제시하고 그 부분의 합의를 기다린다. 미확정 제품 결정 때문에 안전한 독립 작업까지 멈출 필요는 없다. 의존 작업은 보류한다.

## 4. 명세를 코드와 연결한다
각 요구에 `화면 위치 → 재사용 컴포넌트/토큰 → 이벤트 → 상태 변화 → 확인 방법`을 연결한다. 정상, 로딩, 빈 결과, 오류, 성공, 권한 제한을 검토한다. 네트워크 없는 정적 페이지면 로딩/권한은 해당없음과 이유를 적는다. 로딩 중 중복 실행, 오류 후 입력 손실, 이전 응답이 최신 필터를 덮는 경우도 영향 범위에 포함한다.

큰 작업은 한 대표 화면에서 정보 위계·상태·작은 화면을 먼저 확인한다. 대표 화면이 기준을 만족하지 못하면 같은 오류를 여러 화면으로 확장하지 않고 수정한다. 브라우저가 없으면 시각 승인을 완료한 것으로 간주하지 않고 코드 단계까지만 인계한다.

## 5. 실패·중단·복구
- 테스트 실패: 재현 명령과 실패 메시지 보존 → 원인과 영향 분리 → 최소 수정 → 같은 항목과 인접 회귀 재실행.
- 실행 환경 부재: 읽기/정적 검사로 가능한 부분 진행 → 실행/시각 미검증 기록 → 필요한 도구/권한과 한 개의 다음 명령 제시.
- 권한 거부: 금지된 경로/도구를 우회하지 않고 사용자 승인 또는 읽기 전용 산출물로 전환.
- 범위 충돌: 사용자 변경을 보존하고 충돌 파일·선택 필요 사항을 보고. 무관한 리팩터링을 복구 수단으로 넣지 않는다.
- 자산 권한 불명: 라이선스가 확인된 기존 자산/텍스트로 대체하고 불명 자산 사용을 보류.

## 6. 인계 계약
변경 파일과 승인된 결정, 실제 실행 명령/결과, 증거 위치, 실패 수정 후 재검증, 남은 미검증과 담당/다음 조치를 적는다. 정적 추론, 실행 테스트, 브라우저 상호작용, 실제 이미지 열람을 각각 표시한다. ‘확인 예정’은 PASS가 아니다. [검증 체크리스트](review-checklist.md)와 모드별 템플릿으로 대화 없이도 이어받을 수 있게 한다.
